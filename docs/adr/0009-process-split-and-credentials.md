# 0009. 两个进程、一种租户身份

- 状态：Accepted
- 日期：2026-11-13

## 背景

现在所有路由都在 `cmd/server` 里：公开跳转、创建短链、健康检查和指标共用一个进程。跳转是读多写少的公开流量，创建是带 API Key 的写请求。混在一起时，跳转的副本数和故障会绑住管理接口。

阶段 6 已把 API Key 鉴权做进创建接口。密钥是 `slk_` 加 32 字节 `crypto/rand`，库里只存 SHA-256。`api_keys` 没有过期和吊销列，也没有签发入口。能写数据库的人才能插入哈希；已经持有密钥的调用方不能再签发一把。测试和冒烟脚本直接写测试库，按 README 起的空库没有可用密钥。

后面如果做用户操作短链的平台，会再出现人的登录。那是另一种凭证。两种凭证如果各写一套 handler，创建和以后的增删改查会分叉。

## 决策

密钥的过期、吊销和管理员命令先落地。进程拆分仍按下面的边界做，HTTP 管理接口迁到 console 时命令已经在那里。用户、登录和页面留到这条边界稳定之后。

### 两个进程，不是一组微服务

`cmd/redirector` 和 `cmd/console` 是同一个模块里的两个 `main`，部署成两个二进制。它们共用 PostgreSQL、Redis 和 `internal/` 里的包，彼此不发 HTTP 或 RPC。数据所有权不拆开，短码仍然全局唯一。

这是按流量和故障域把一个服务部署两次。Java 里接近同一个仓库的两个 Spring Boot 应用，共用库和一块领域代码。微服务还要各自拥有数据，并通过网络互相调用；那一步现在没有收益，两个进程之间也没有调用链。

| 进程 | 职责 |
| --- | --- |
| `redirector` | `GET /r/{code}`、`/healthz`、`/metrics`。读缓存，未命中回源，成功的 GET 记点击。不挂管理路由，不签发密钥 |
| `console` | `POST /api/v1/links`、`/healthz`、`/metrics`，以及以后的增删改查。创建时继续写穿缓存。API Key 鉴权只留在这里 |

每个进程各自监听，各自暴露指标。扩容时只加 redirector 副本。

### 谁可以发密钥

当前没有管理员角色，也没有用户表。签发权等于数据库写权限，也就是服务的运维人员。

闭环用 `cmd/console` 的运维命令完成，不提供公开的签发 HTTP 接口：

- `key issue --name` 创建租户并调用 `GenerateAPIKey`；`--tenant` 给已有租户再发一把。
- 明文只在命令的标准输出里出现一次，库里只写哈希。`key list` 只打印编号和时间，`key revoke --id` 按签发时打印的密钥 ID 吊销。
- `expires_at` 和 `revoked_at` 都可空。空的 `expires_at` 表示不过期，和链接同一套规则。鉴权时过期或已吊销仍返回 401，响应不区分这几种失败。

持有 `slk_` 的调用方仍然不能用这把密钥再签发密钥。

### 以后的用户平台

人的登录和机器的 API Key 是两种凭证，最后都写成 context 里的同一个 `tenant.Tenant`。handler 继续只读 context，不解析 `Authorization`。Java 里相当于表单登录、JWT 和 API Key 三种 Filter 产出同一个 `Authentication`，controller 只注入主体。

平台按这个顺序接，创建和跳转不用改：

1. 用户、密码或单点登录、会话放在平台里。浏览器只持有会话 cookie 或短寿命 JWT，不持有 `slk_`。API Key 放在别的系统的服务器上。
2. 租户仍是数据边界。用户和租户用成员表相连，成员带角色。本服务继续用 `tenants.id`。平台若在外部，把它的租户编号写入已经留好的 `external_id`。
3. console 保留现在的 API Key 中间件。人从页面进来时，另一个中间件检查会话或网关已经验过的身份，查出成员关系，放进同一个 context。短链只信任来自网关的身份，浏览器不直接拿 API Key 调管理接口。
4. 租户管理员在页面上签发密钥。服务端仍调用 `GenerateAPIKey`，明文只返回一次。注册流程创建租户和第一名所有者。运维命令只负责还没有平台注册时的第一把引导密钥。
5. 列表、修改、删除加上 context 里的 `tenant_id`。其他租户的短链按找不到处理。`/r/{code}` 保持公开。

用户表、登录、页面和短链的增删改查都不在这次拆分里做。

## 后果

- 跳转和管理可以分开扩容、分开重启。两边仍共享数据库，库是共同的故障点。
- 两个进程的 `/healthz` 和 `/metrics` 要分别抓取。OpenTelemetry 仍然先不做：进程之间没有调用，追踪看的是单个请求内部的耗时（[ADR 0005](0005-prometheus-before-tracing.md)）。
- 多个 redirector 副本之后，缓存击穿才需要单独的多副本方案；那一项保持可选。
- 管理员命令在 `cmd/console`：`key issue`、`key list`、`key revoke`。`cmd/server` 在拆分完成前继续提供全部 HTTP。命令不依赖 Redis。空库要先签发一把密钥，创建接口才调得通。不要加公开的签发路由。
- handler 只读 context 里的租户。以后加会话或网关中间件时，不改创建逻辑。
