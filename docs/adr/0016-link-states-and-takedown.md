# 0016. 链接状态和下架：过期、停用、封禁

- 状态：Accepted
- 日期：2026-11-18

## 背景

现在让一条短链停止跳转只有两个办法：等它过期，或者硬删除。

- 租户没有「先停一下」。删除会连统计一起删掉，不能恢复，短码也可能被以后的新链接随机生成。
- 平台没有任何手段处理违规链接（钓鱼、色情、赌博、毒品等）。只能直接改库，改完之后缓存里的旧值还能继续跳转最长 1 小时。

后面会加两样东西，现在的设计要给它们留位置：租户自己操作短链的前端页面；创建之后异步执行的 AI 风控，发现违规内容时自动下架。

现有约束：

- 跳转读缓存，正缓存 TTL 最长 1 小时。管理写在数据库提交后无条件覆盖缓存，回源用 `SET NX`（[ADR 0011](0011-link-crud-api.md)）。下架必须走这套协议，否则「已下架」的链接还会继续跳。
- 管理视角和跳转视角对过期链接的语义已经分开：管理可见、可改，跳转 404（ADR 0011）。
- 运维命令（`key`、`tenant`）只连 PostgreSQL，不连 Redis（[ADR 0009](0009-process-split-and-credentials.md)）。
- 没有人类用户和后台角色。平台侧的操作入口只有 `cmd/console` 的运维命令。
- 创建计入本月配额，之后发生什么都不返还（[ADR 0015](0015-monthly-link-quota.md)）。

## 决策

### 三个独立的事实，不是一个状态字段

| 状态 | 谁决定 | 存储 | 谁能撤销 |
| --- | --- | --- | --- |
| 过期 `expired` | 租户预先设定，到时间自动成立 | `expires_at`（已有），不落状态 | 租户把 `expires_at` 改到将来或清空 |
| 停用 `disabled` | 租户 | `disabled_at` | 租户 |
| 封禁 `banned` | 平台：运维命令，以后还有风控 | `banned_at`、`ban_reason`、`ban_source` | 只有平台 |

- 三者可以同时成立：一条已停用的链接可以再被封禁，解封后它仍然是停用的。存成一个 `status` 枚举的话，后一个状态会盖掉前一个，解封时不知道该回到哪里。
- 过期仍然是算出来的：`expires_at` 和当前时间比较，不需要任务去翻状态。
- 存时间戳而不是布尔值，和 `api_keys.revoked_at` 同一个写法，顺带记下发生的时间。

迁移 006 给 `links` 加四个可空列和三个 CHECK：

```sql
ALTER TABLE links
    ADD COLUMN disabled_at TIMESTAMPTZ,
    ADD COLUMN banned_at   TIMESTAMPTZ,
    ADD COLUMN ban_reason  TEXT,
    ADD COLUMN ban_source  TEXT,
    ADD CONSTRAINT ck_links_ban_fields CHECK (num_nulls(banned_at, ban_reason, ban_source) IN (0, 3)),
    ADD CONSTRAINT ck_links_ban_reason CHECK (ban_reason IN ('phishing', 'malware', 'adult', 'gambling', 'drugs', 'spam', 'other')),
    ADD CONSTRAINT ck_links_ban_source CHECK (ban_source IN ('operator', 'risk'));
```

封禁的三个字段同有同无。不加索引：跳转按 `code` 的唯一索引找到行再过滤，列表不按状态筛选。

对外给一个派生的 `status`，按这个顺序取第一个成立的：`banned`、`disabled`、`expired`、`active`。顺序按租户自己能不能解决来排：封禁要找平台，停用和过期自己能改。

### 跳转：三种状态都当作找不到

- `GetByCode` 的查询加上 `AND disabled_at IS NULL AND banned_at IS NULL`，和过期一样在 SQL 里滤掉，返回 `link.ErrNotFound`，redirector 照旧 404。redirector 的 handler 和 `httpapi.LinkStore` 接口都不用改。
- 响应不区分状态。访问者看不出一条链接是不存在、过期、停用还是被封禁。
- 不可跳转的短码走负缓存，TTL 1 分钟，热门短码每分钟最多回源一次，和已删除的链接一样。

### 可不可以跳转只有一个判断

`link.Link` 增加 `DisabledAt` 和封禁信息（时间、原因、来源），以及两个方法：

- `Status(now)`：按上面的优先级返回状态。
- `Servable(now)`：状态是 `active`。

用到它的地方：

- `cache.Store` 在管理写之后决定写正缓存还是负缓存。现在这里只看 `Expired`。
- `cache.Store.GetByCode` 命中正缓存时再判断一次。现在这里只看 `Expired`；带着停用或封禁信息的正缓存按找不到处理并删掉 key，防写缓存的地方漏判。
- SQL 里的过滤条件是它的等价写法，集成测试对着同一组用例验证两边一致。

### 租户停用和启用

- `PATCH /api/v1/links/{code}` 多接受一个字段 `disabled`：`true` 停用，`false` 启用，没出现表示不改。`null` 和非布尔值返回 400。可以和 `url`、`expires_at` 在一次请求里一起改。
- 重复停用保留第一次的时间（`COALESCE(disabled_at, now())`），启用把它清成 NULL。两个操作都幂等。
- 停用的链接仍然可以改 URL、改过期时间、看统计、删除。
- 不单独开 `POST .../disable` 这样的动作接口。停用是链接的一个字段，已有的 PATCH 语义、原子 `UPDATE` 和缓存维护直接够用。

### 平台封禁和解封

入口是运维命令，不加 HTTP 接口：

```bash
console link ban --code CODE --reason REASON
console link unban --code CODE
```

- 按短码操作，不需要租户 ID。`--reason` 必填，取值 `phishing`、`malware`、`adult`、`gambling`、`drugs`、`spam`、`other`。
- 存储层只有一个封禁入口 `Ban(ctx, code, reason, source)`。运维命令传 `source = operator`；以后风控调同一个方法，传 `risk`。
- 封禁先到先得：已封禁的链接再封一次，保留第一次的时间、原因和来源，照样返回这一行。命令可以放心重跑。要改原因时先解封再封禁。
- 解封把三个字段一起清空。没被封禁的链接解封是空操作。短码不存在返回 `link.ErrNotFound`。
- 原因是封闭的类别集合，不是自由文本：它会原样出现在租户的 API 响应里，前端要能按类别给文案。Go 里定义类型和校验，数据库 CHECK 兜底；加类别要改这两处并加迁移。

### 被封禁的链接对租户只读

- 详情、列表、统计照常返回，带 `status: "banned"`、`banned_at` 和 `ban_reason`。`ban_source` 不对外。
- `PATCH` 和 `DELETE` 返回 403 和 `{"error":"link is banned"}`，新增领域错误 `link.ErrBanned`。
- 不能改：平台审核和封禁的是「这个短码指向这个内容」。封禁期间允许改 URL，解封时放行的就不是当初审核的内容，被封的原始 URL 也不再有记录。
- 不能删：现在没有单独的封禁记录表，链接这一行就是封禁记录。删除是硬删除，删了之后违规的 URL、原因和归属租户都没了，申诉、复核和以后按租户累计违规都没有依据。有了独立的封禁记录表之后可以放开删除，修改仍然不放开。
- 用 403 不用 404：链接是租户自己的，它存在这件事不需要隐藏；返回 404 的话租户分不清是自己删了还是被封了。其他租户的链接不管封没封都还是 404。
- 存储层的写法：`Update` 的 `WHERE` 加 `banned_at IS NULL`，没更新到行时补查一次，区分「不存在」和「已封禁」，和 `RevokeAPIKey` 区分「不存在」和「已吊销」是同一个写法。`Delete` 在事务开头已有的 `SELECT ... FOR UPDATE` 里一并读出是否封禁。

### 缓存

- 停用、封禁：数据库提交后无条件 `SET` 负缓存，和删除一样。
- 启用、解封、其他修改：提交后按 `Servable` 决定。可跳转写正缓存，否则写负缓存，比如解封了但仍然停用。
- 管理写在写完正缓存之后，再按跳转查询读一次库；读到的是找不到，就补写负缓存。这一步和缓存写入一样不跟随请求取消。原因见下面的「下架和管理写交错」。
- 复查读库出错（超时、库故障）时同样补写负缓存，并记一条日志：复查偏向不跳转，宁可让这条链接最多多 404 一分钟（负缓存过期后回源自愈），也不让可能已经被下架或删除的链接继续跳。这是有意的取舍。
- 封禁和解封要把缓存写失败报给调用方。现在 `writeCache` 失败只记日志和指标，对修改和删除这是可以接受的最终一致（ADR 0011）；被封禁的链接如果正缓存没被盖掉，还能继续跳转最长 1 小时，而封禁的对象往往正是不能再多跳一小时的内容。`writeCache` 改成返回 error，`Update`、`Delete` 照旧只记不报，`Ban`、`Unban` 把它返回。
- 运维命令因此要连 Redis。`console link` 读 `REDIS_URL`，`key` 和 `tenant` 命令不变。顺序是先写库、再写缓存，Redis 不可用不拦封禁：
  - 库写成功、缓存写失败：命令退出码非 0，输出说明「已封禁，缓存未更新」。重跑同一条命令即可，封禁幂等，重跑只是再写一次缓存。
  - Redis 整个不可用：封禁照样落库。redirector 这时读缓存也失败，走数据库回源，回源查询已经过滤了封禁。Redis 恢复后旧的正缓存可能还在，要重跑命令。
  - 没人重跑的最坏情况：旧的正缓存活到 TTL，最长 1 小时。

### 下架和管理写交错

ADR 0011 接受了一个窗口：两个管理写并发时，缓存 `SET` 的顺序可能和数据库提交的顺序相反，缓存落后到 TTL。当时交错的两方都是租户自己。封禁让两方的利益相反了：

```txt
租户 PATCH 提交（这时还没封禁）
平台封禁提交
平台 SET 负缓存
租户 SET 正缓存        <- 晚到的旧值盖掉了负缓存，被封禁的链接继续跳转最长 1 小时
```

租户不需要知道封禁什么时候发生，持续发 PATCH 就能提高撞上的概率。

处理办法是上面的复查：租户的写在 `SET` 正缓存之后再读一次库。

- 复查读到了封禁：补写负缓存，它排在自己那次正缓存之后。
- 复查没读到封禁：说明封禁在复查之后才提交，封禁自己的负缓存写入更晚，同样排在正缓存之后。

两种情况最后落在缓存里的都是负值。同样的顺序也覆盖了「删除和修改交错」「停用和修改交错」「解封和停用交错」。它只保证不可跳转的链接最终不在正缓存里；两个都可跳转的值谁先谁后（比如两次改 URL）仍然是 ADR 0011 接受的窗口，要靠版本号解决。

复查偏向不跳转：补写的负缓存如果盖掉了一次刚好同时发生的启用或解封，这条链接会多 404 最长 1 分钟，负缓存过期后回源自愈。

创建不做复查：短码在创建响应返回之前没有人知道，没有谁能在这个窗口里下架它。风控上线后这个前提不再成立（它在创建提交时就能拿到短码），到时候创建的缓存写入也要加上复查。

### 给异步风控留的位置

这一期不实现风控，只保证加它的时候不用推翻现在的设计：

- 封禁入口只有 `Ban` 一个，带来源和原因。风控是它的第二个调用方。
- 风控的触发条件是「链接的 URL 变了」：创建和修改 URL 都要送审。只审创建的话，可以先建一条干净的链接，过审后再把 URL 改成违规内容。封禁后只读挡住了反方向：被封的链接不能靠改 URL 换内容。
- 风控是异步的：创建接口不等审核结果，链接先生效，违规的事后封禁。审核完成之前违规链接是可以访问的。
- 待审核的任务要落库，不能只放内存队列，进程重启不能丢审核。到时候加一张待办表，创建、修改和入队放在同一个事务里，worker 用 `FOR UPDATE SKIP LOCKED` 取任务。
- worker 要去抓取租户提交的 URL，必须防 SSRF：内网地址、重定向、超时和响应大小。
- 误封由运维用 `unban` 解除。`ban_source` 记下了哪些是风控封的，方便统计误判。

## 不做什么

- 不给跳转做区分状态的响应（410、451 或「链接已被封禁」页面）。统一 404；有了前端和品牌页面之后再决定封禁要不要单独的落地页。
- 不做租户级封停。现在的办法是吊销它的 API Key，再逐条封禁。
- 不做 URL 或域名黑名单，也不在创建时同步拦截。被封的租户可以用同一个 URL 再建一条新链接，这要靠风控和租户封停解决，这一期不防。
- 不做风控本身：待办表、worker、扫描结果、申诉流程都不在这一期。
- 不建封禁记录表和操作审计。解封会清空封禁字段，不留「曾经被封过」的历史，谁执行的命令也没有记录。
- 不提供封禁和解封的 HTTP 接口。平台侧还没有身份和权限模型，运维命令的访问控制就是谁能登上机器。
- 不做列表的状态筛选。前端需要时再加；过期是算出来的，按它筛选要单独设计查询。
- 不做软删除和回收站。停用已经覆盖了「先停一下，以后可能恢复」；删除仍然是硬删除（ADR 0011）。
- 不返还配额。停用、封禁、删除都不改变本月用量（ADR 0015）。

## 怎么验证

- `internal/link` 单测（表驱动）：`Status` 的优先级，同时封禁、停用、过期时是 `banned`，停用且过期是 `disabled`；`Servable` 只在 `active` 时为真；到期时刻本身算过期。
- `internal/postgres` 集成测试：
  - 过期、停用、封禁的链接 `GetByCode` 都返回 `ErrNotFound`；`GetForTenant` 和 `List` 照常返回并带上状态字段。
  - 重复停用不改时间；停用期间可以改 URL；启用后恢复跳转。
  - `Update`、`Delete` 遇到被封禁的链接返回 `ErrBanned`，数据不变；其他租户的被封禁链接仍是 `ErrNotFound`。
  - `Ban` 重复调用保留第一次的时间、原因和来源；`Unban` 之后仍然停用的链接不可跳转。
  - CHECK 拒绝只填一部分的封禁字段，以及列表之外的原因和来源。
- `internal/cache` 测试：
  - 停用、封禁后缓存是负值；启用、解封后是新的正值；解封一条仍然停用的链接写负值。
  - Redis 不可用时 `Ban` 返回缓存未更新的错误，而下游的 `Ban` 已经执行；重跑成功。
  - 管理写写完正缓存后，下游按跳转查询已经找不到这条链接：缓存最终是负值。
  - 命中带停用或封禁信息的正缓存，返回找不到并删掉 key。
- `internal/httpapi` httptest：`PATCH {"disabled":true}` 和 `false`；`null`、非布尔值返回 400；空对象的错误信息带上新字段；被封禁的链接 `PATCH`、`DELETE` 返回 403 和 `{"error":"link is banned"}`；响应里的 `status` 和三个可选字段。
- `cmd/console` 测试：`link ban` 缺 `--reason`、原因不在列表里是用法错误（退出码 2）；库写成功、缓存写失败时退出码 1 并提示重跑；`key`、`tenant` 命令仍然不读 `REDIS_URL`。
- `make smoke`：创建后 302；`PATCH {"disabled":true}` 后 404，详情的 `status` 是 `disabled`；启用后 302；`console link ban` 后 404，详情的 `status` 是 `banned`，`PATCH` 和 `DELETE` 都是 403；`console link unban` 后 302。
- `make selfcheck` 的迁移 up、down、up 覆盖 006 的回滚。
- 2026-11-18：草稿 SQL 在一次性的 PostgreSQL 17 实例上手工跑过：三个 CHECK 各自拒绝了对应的坏数据；停用、重复停用、停用期间改 URL、启用；封禁后跳转查询查不到；重复封禁保留第一次的值并返回行；修改被封禁的链接不更新任何行，补查为已封禁，URL 没变；其他租户的短码补查为不存在；解封后三个字段一起清空；停用加封禁的链接解封后仍然查不到；down 删列时三个 CHECK 一起消失。缓存和复查的部分随后由 `internal/cache` 单测覆盖（封禁/解封写缓存、Redis 不可用时重跑、复查补写负缓存），`internal/postgres/cache_seam_test.go` 重放本 ADR 的交错并确认最终是负值，`make smoke` 覆盖封禁后 404、租户写 403、解封后 302。

## 后果

- 下架有了三档：租户可逆的停用，平台强制的封禁，不可逆的删除。
- 管理响应多了 `status`、`disabled_at`、`banned_at`、`ban_reason`，后三个为空时省略。都是新增字段，不破坏兼容。ADR 0011 里「客户端根据 `expires_at` 判断」改为读 `status`。
- `link.Link` 多了字段，缓存里的 JSON 跟着变长。旧的缓存值没有这些字段，解出来是空，等同于没停用、没封禁，不需要清缓存。
- 管理写多一次读库：写了正缓存的修改、启用和解封各多一次按 `code` 的查询。管理写低频，接受。
- 运维命令第一次需要 Redis。`console link` 在 Redis 不可用时仍然能封禁，但要重跑才能确定缓存已经更新。
- 封禁多久生效取决于缓存写入：写成功，之后开始的请求立即 404，已经在途的请求可能还会 302 一次（和 ADR 0011 的删除相同）；写失败又没人重跑，最长 1 小时。
- 迁移 006 只加可空列和约束，旧版本进程照常运行，但旧版本不认识新列：旧 redirector 不过滤停用和封禁，旧 console 的修改会把停用的链接写回正缓存。发布顺序是迁移、换完 redirector 和 console、再开始使用停用和封禁。
- 给 `links` 加 CHECK 会在排他锁下扫一遍全表。表大了之后改成 `NOT VALID` 加 `VALIDATE CONSTRAINT` 两步。
- 存储指标新增操作 `ban`、`unban` 和结果 `banned`。租户改、删被封禁的链接是策略生效，不算存储失败。
- 被封禁的链接租户删不掉，会一直留在列表里，直到平台解封或以后有了封禁记录表。
- 需要同步的文档：`docs/api.md`（`disabled` 字段、响应字段、403、跳转一节、指标的 label）、`docs/architecture.md`（表结构、缓存规则、运维命令）、`docs/runbook.md`（新增「封禁和解封链接」，包括缓存没更新时怎么办）、`console` 的用法说明。

## 备选方案

- **一个 `status` 枚举列**：读起来直观，但三个事实会互相覆盖，解封、启用时要记住「之前是什么」，过期还得有任务去翻状态。
- **封禁放在单独的表里，`links` 不加列**：能留历史。但跳转回源要多关联一张表，而现在没有审计需求。以后要历史时再建记录表，`links.banned_at` 继续作为跳转过滤用的当前状态。
- **封禁就是删除**：最简单。但证据没了，短码可能被重新生成，租户看不到发生了什么，也没法解封。
- **缓存值带版本号，写入前用 Lua 比较**（ADR 0011 提过）：能解决所有管理写的乱序，包括 URL。改动大；复查只解决「可不可以跳转」这一半，够下架用。
- **封禁后隔一会儿再写一次负缓存**：不用改租户的写路径。但命令里要等待，风控还得自己调度第二次写，等多久也只能估。
