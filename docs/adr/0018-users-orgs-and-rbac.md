# 0018. 用户、组织和权限

- 状态：Accepted
- 日期：2026-11-19

## 决策

| 决策点 | 选择 |
| --- | --- |
| 1a 租户和组织 | 组织就是现有租户，`tenants` 表不变，加成员表 |
| 1b 用户和组织的关系 | 多对多，`memberships(user_id, tenant_id, role)` |
| 2 身份功能放在哪里 | 放进 console，代码在独立的 `internal/identity` 包 |
| 3 会话机制 | 服务端会话，存 PostgreSQL |
| 4 登录方式 | 只用 OAuth / OIDC，不存密码；目的是学完整的授权码流程 |
| 4b 第一个身份提供方 | 本地 Dex（compose 里的标准 OIDC 服务）；GitHub 留作第二个提供方对比 |
| 5 权限模型 | 固定角色，代码里映射权限；handler 只调 `can`；API Key 带 scope 和 `created_by` |
| 6 当前组织 | 请求头 `X-Org-ID`，只对会话请求生效 |

## 背景

现在只有机器身份：一把 `slk_` API Key 对应一个租户，拿到 Key 就拥有这个租户的全部权限。
租户和 Key 都靠运维跑 `console key issue` 开出来（[ADR 0009](0009-process-split-and-credentials.md)）。

后面的审计日志要记“谁做的”，Webhook 要按组织配置，计费要挂在组织上，都需要先有“人”和“人在组织里能做什么”。
ADR 0009 已经留了口子：人和 API Key 是两种凭证，最后写进 context 的是同一个身份，handler 不用改。

这篇 ADR 先列出要选的六个决策点。每个点给出选项、代价和推荐，选完后把“决策”一节补齐，状态改成 Accepted。

### 做选择时用的几把尺子

后面每个决策点都会用到其中几把，先列在这里：

- **可逆性**：改主意的代价有多大。表结构、对外的 URL、已经发出去的凭证格式是“单向门”，
  一旦有数据或客户依赖就很难回头；内部函数、包结构是“双向门”，随时能改。单向门要多想，双向门先做简单的。
- **和已有原则一致**：仓库里已经定过的规矩（Redis 可以挂、数据库是唯一事实来源、handler 只读 context）
  比新方案的局部优点更重要。原则不一致的系统，每个人都要记住例外。
- **故障半径**：一个组件出问题会波及多少人、多少功能。
- **安全责任**：存下来的每一份敏感数据（密码哈希、会话）都是要负责的东西，少存就少负责。
- **可测试性**：能不能在 `go test` 里不联网、不依赖外部账号就测完整条路径。
- **YAGNI 但留缝**：不为想象中的需求写代码，但让以后加它时不用推倒重来。

## 决策点 1：组织模型

### 1a. 租户和组织是不是同一个东西

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A. 组织就是现有租户** | 继续用 `tenants` 表，对外叫“组织”，加成员表 | 不动 `links.tenant_id`、配额、限流、统计；迁移最小 | 以后想做“一个组织下多个项目”要再加一层 |
| B. 新建组织，租户挂在组织下 | `organizations` 1 对多 `tenants`（类似 Vercel 的 Team 和 Project） | 一开始就支持多项目，配额可以按项目分 | 每张表、每条查询都要想“按组织还是按租户”；现在没有需求 |

**权衡**：B 的好处来自一个还不存在的需求。A 以后要变成 B，只要新增一层 `organizations` 并让
`tenants` 指过去，现有数据不用重写，所以 A 是**可逆的**，B 是提前付出复杂度。

**推荐 A。**

### 1b. 一个用户能不能属于多个组织

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A. 一人一组织 | `users.tenant_id` | 简单，登录后组织就确定了 | 顾问、外包、同时在两家公司的人要注册两个账号；以后改成多对多要迁移数据 |
| **B. 多对多** | `memberships(user_id, tenant_id, role)`（GitHub、Slack 的做法） | 符合真实世界；角色天然挂在成员关系上 | 每个请求都要回答“这次操作的是哪个组织”（见决策点 6） |

**权衡**：这是**单向门**。A 改成 B 时，用户表里的 `tenant_id` 和挂在它上面的角色都要搬家；
B 退化成“只允许一个”只需要加一条唯一约束。单向门上宁可一开始多付一点。

**推荐 B。**

## 决策点 2：身份功能放在哪里

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A. 放进 console** | 注册、登录、会话、成员管理都是 console 的新路由和新包 | 一个部署单元；和现有鉴权在同一个中间件链里；测试用 httptest 全覆盖 | console 的职责变多；以后拆出去要搬代码 |
| B. 新进程 `cmd/platform` | 独立进程负责身份，console 通过网关信任它签的身份 | 故障域分开，身份服务可以单独扩容 | 两个进程要约定身份怎么传递（头、签名），多一个部署、多一套信任关系 |
| C. 外部身份服务 | Auth0、Keycloak、Zitadel 等，本服务只验它签发的令牌 | 不用自己存密码，SSO、MFA 现成 | 学不到身份系统本身；测试依赖外部服务或要自己模拟；有供应商锁定 |

**权衡**：ADR 0009 写的是“平台在外部，短链只信任网关传来的身份”，那是在不知道平台长什么样时留的最宽的口子。
现在要自己做平台：

- 拆进程的理由是**流量和故障域不同**（ADR 0009 拆 redirector 就是因为跳转流量远大于管理流量）。
  登录和管理 API 的流量量级相同、使用者相同，拆开没有这个收益。
- C 在生产上常常是对的（安全责任外包），但这个项目的目标是学 Go 写 SaaS，C 正好把要学的部分外包掉了。
- A 只要守住 ADR 0009 的那条原则（**handler 只读 context 里的身份**），以后拆成 B 或换成 C 都只换中间件。

**推荐 A**，并把身份相关代码放进独立的包（例如 `internal/identity`），方便以后搬走。
选 A 会修改 ADR 0009“以后的用户平台”第 1、3 条：平台不在外部，网关信任这一步暂时不需要。

## 决策点 3：会话机制

浏览器登录后要带一个凭证证明“我已登录”。

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A. 服务端会话** | 随机 token 放 HttpOnly Cookie，库里存 token 的哈希和过期时间 | 登出、踢人、禁用用户**立刻生效**；token 本身不含信息，泄露了也只是一个随机串 | 每个请求查一次库 |
| B. 无状态 JWT | 登录时签一个 JWT，服务端只验签，不查库 | 不查库，多服务共享验签很方便 | 签发后到过期前**无法撤销**；要撤销只能加黑名单，又变回查库；密钥轮换、算法混淆攻击要处理 |
| C. 短 JWT 加刷新令牌 | 5 到 15 分钟的 JWT 加存在库里的刷新令牌 | 撤销延迟缩短到 JWT 寿命 | 两套机制的复杂度；撤销仍然不是立刻 |

**权衡**：JWT 的核心卖点是“不用查库”。看一下这个项目的现实：

- 现在的 API Key 鉴权**每个请求都查库**，并且靠这一点让“改限流下一次请求就生效”（ADR 0014）。
  会话鉴权反正也要查成员关系和角色，省掉一次会话查询意义不大。
- 这个项目一贯偏向“改了马上生效”：封禁要复查缓存（ADR 0016），吊销 Key 立刻 401。
  B 意味着“把用户踢出组织后，他还能操作 15 分钟”，和已有原则冲突。
- JWT 真正有优势的场景是多个独立服务都要验身份、又不想都连身份库。我们只有 console 一个验证方。

**推荐 A。** 这也是 ADR 0009 第 1 条“浏览器只持有会话 cookie”的落地。

### 3b. 会话存在哪

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **PostgreSQL** | 和 API Key 一样存在事实来源里；Redis 挂了不影响登录 | 每次请求一条主键查询（和 API Key 鉴权同一个量级） |
| Redis | 快，TTL 自动过期 | Redis 挂了**所有人被登出**或无法鉴权 |

**权衡**：ADR 0006 定过“Redis 是缓存，可以挂，挂了要能降级”。把会话放 Redis，Redis 就从“可以挂”变成“挂了没人能用管理功能”，
**故障半径**变大，而且破坏了已有原则。性能不是问题：管理流量很小，现在每个请求已经在查 API Key。

**推荐 PostgreSQL。** 过期的会话由查询条件过滤，清理可以以后交给后台任务（阶段 13）。

## 决策点 4：登录方式

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **A. 邮箱加密码（argon2id）** | 不依赖外部服务，测试完全离线；能学到密码哈希、常量时间比较、防暴力破解、账号枚举防护 | 要为存下的密码哈希负责；找回密码需要发邮件（还没有） |
| B. 只用 OAuth / OIDC（GitHub、Google） | 不存密码，安全责任小；用户体验好 | 测试要模拟身份提供方；本地开发要注册 OAuth 应用；要学 state、PKCE、ID Token 校验 |
| C. 邮件魔法链接 | 不存密码 | 依赖发邮件，现在没有可靠的后台任务和邮件通道 |

**权衡**：生产上很多新 SaaS 选 B，原因就是**安全责任**：不存密码，就不会泄露密码。
但作为学习路线，A 先做有两个理由：

- A 的每一步都能在 `go test` 里测（**可测试性**），而且覆盖的是身份系统的基本功；
  做过 A 再做 B，会清楚 OIDC 替你省掉了哪些事。
- 认证方式是**双向门**：用户表和会话表不变，以后加 B 只是多一种“验证完身份后创建会话”的入口。

A 的已知缺口：没有邮箱验证和找回密码。这两件都要发邮件，而可靠发邮件需要阶段 13 的 Outbox 和后台任务。
在那之前，注册的邮箱不验证，不开放公网注册。

**推荐 A，OAuth 作为后续阶段。** 密码哈希用 `golang.org/x/crypto/argon2` 的 argon2id，参数写进代码注释并说明来源。

**选择：B，只用 OAuth / OIDC。** 目的是学完整的授权码流程。没有选推荐的 A，接受的代价和对应的做法：

- 可测试性：测试不连真实的身份提供方，用 `httptest.NewServer` 写一个假的 OIDC 服务
  （发现文档、授权端点、令牌端点、JWKS），覆盖成功、state 不符、code 过期、签名错误、nonce 不符。
- 用户的身份是 `(issuer, subject)`，不是邮箱。`user_identities` 表上 `(issuer, subject)` 唯一。
  第一版一个用户只有一个身份，**不按邮箱自动关联**：一个提供方的邮箱没验证过时，按邮箱合并账号可以被用来接管别人的账号。
- 引导：运维命令 `console member invite --tenant --email --role` 预先登记邀请。
  某人第一次登录时，ID Token 里的 `email` 和邀请相同、并且 `email_verified` 为 true，才把他加进组织。
  没有邀请的人可以登录，但不属于任何组织，管理接口对他一律 404。
- 自己写流程，不自己写密码学：跳转、state、PKCE、回调、建会话这些 handler 自己写，这是要学的部分；
  授权码换令牌用 `golang.org/x/oauth2`，ID Token 的签名和声明校验用 `github.com/coreos/go-oidc/v3`。
  JWT 验签、JWKS 缓存和密钥轮换容易写错，出错就是安全漏洞，交给经过审查的库。

### 4b. 第一个身份提供方

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| **A. 本地 OIDC 服务（Dex，放进 docker-compose）** | 完整的标准 OIDC（有 ID Token、发现文档）；离线可用，`make smoke` 和 CI 都能跑真实流程；配置文件里写死测试用户 | 不是真实用户会用的登录方式；compose 多一个服务 |
| B. GitHub | 开发者都有账号，最接近真实产品 | GitHub 的用户登录是纯 OAuth 2.0，**没有 ID Token**，要拿 access token 再调 `/user` 接口，学不到 OIDC 的那一半；CI 跑不了真实流程 |
| C. Google | 标准 OIDC | 国内网络访问不稳定；同样进不了 CI |

**权衡**：OIDC 是一个标准，代码只依赖标准里的发现文档和 ID Token，换提供方只换配置（issuer、client id、secret）。
所以先用最容易测试、最符合标准的那个把流程做对，真实提供方以后只是加配置；GitHub 因为不走 OIDC，要单独写一条分支。

**推荐 A，GitHub 作为第二个提供方单独做一次**（那时能对比 OAuth 2.0 和 OIDC 差在哪）。

**选择：A。** 先用 Dex 把标准 OIDC 闭环跑进 `make smoke` 和 CI，之后再把 GitHub 作为第二个提供方单独接一次。

## 决策点 5：权限模型

### 5a. 角色和权限怎么建模

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A. 固定角色，代码里映射权限** | 成员关系上一个 `role` 枚举（owner、admin、member、viewer），代码里一张表把角色映射到权限 | 简单，一眼能看清谁能做什么；权限检查写成 `can(principal, PermLinksWrite)` | 客户不能自定义角色 |
| B. 角色和权限都在库里 | `roles`、`role_permissions` 表，组织可以自定义角色 | 灵活，企业客户会要 | 管理界面、缓存、迁移都变复杂；现在没有客户 |
| C. 策略引擎（Casbin、OPA） | 用 DSL 描述规则，支持属性条件（ABAC） | 规则可以非常细 | 多一门语言和一个依赖；对四个角色是重型武器 |

**权衡**：关键不在选哪个，而在**检查权限时检查什么**。
handler 里写 `if role == "admin"` 的话，以后从 A 换 B 要改每个 handler；
写 `can(p, PermLinksDelete)` 的话，角色到权限的映射从代码换成库，handler 一行不动。
这就是 Spring Security 里 `hasRole` 和 `hasAuthority` 的区别。

**推荐 A，并且 handler 只检查权限、不检查角色。**

**选择：A。** 实现上就是策略模式：handler 依赖一个小接口（例如 `Authorizer`，一个 `Can` 方法），
第一版的实现是一张 Go 的 map（角色到权限）。以后想学策略引擎时，在同一个接口后面换成 Casbin 实现，
handler 不改。这次替换可以作为单独的练习，用来检验接口抽得对不对。
注意“策略引擎”（Policy Engine，按规则判断能不能做）和“策略模式”（Strategy Pattern，同一个接口换不同实现）
是两个概念，名字里的“策略”对应的英文不同。

固定角色权限表如下：

| 角色 | 拥有权限 |
| --- | --- |
| `viewer` | `links:read`、`stats:read`、`members:read` |
| `member` | `links:read`、`links:write`、`stats:read`、`members:read` |
| `admin` / `owner` | 以上全部 + `members:write`（`owner` 与 `admin` 的资源级区别，例如 `admin` 不能修改或移出 `owner`，留到成员管理 handler 中按目标成员角色检查） |

路由级权限校验收口在 `consoleRoute` 的 `requirePerm` 中间件里调用 `Authorizer.Can`，防止新增路由漏写检查；涉及具体资源的规则仍可在 handler 内继续调用 `Authorizer.Can`。

### 5b. API Key 的权限

| 选项 | 好处 | 代价 |
| --- | --- | --- |
| A. Key 拥有组织的全部权限（现状） | 不用改 | 给一个只需要读统计的脚本发 Key，它也能删光所有链接 |
| **B. Key 带 scope**（`links:read`、`links:write`、`stats:read`） | 最小权限；和人的权限用同一套 `Perm` | 签发时要选 scope；老 Key 要迁移成“全部 scope” |
| C. Key 属于个人（个人访问令牌） | 能追溯到具体的人 | 人离开组织后 Key 跟着失效，自动化脚本会突然坏掉 |

**权衡**：B 让 Key 和人走同一条权限检查路径：人的权限来自角色，Key 的权限来自 scope，handler 只看最终的权限集合。
C 适合 GitHub 那样以个人为中心的产品；短链的 Key 多半给服务器上的脚本用，应该属于组织。
可以给 Key 记一个 `created_by`，审计时仍然能追溯到签发人。

**推荐 B，加 `created_by`。** 存量 Key 迁移成全部 scope，行为不变。
`PATCH` 成功时，只有同时具备 `links:read` 才返回链接对象；只有 `links:write` 返回 204，避免写权限把 `url` 和点击数读出来。

## 决策点 6：请求怎么确定“当前组织”

用户可以属于多个组织（决策点 1b 选 B 时），每个请求都要知道操作的是哪个组织。API Key 不受影响：Key 本来就属于一个组织。

| 选项 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A. 放在 URL 里 | `/api/v1/orgs/{org}/links` | 显式、可加书签、日志里一眼看出；REST 风格（GitHub API） | **现有路由全部要变**，API Key 调用方也要改；或者两套路由并存 |
| **B. 放在请求头里** | `X-Org-ID: 42`，只对会话请求生效 | 现有 `/api/v1/links` 不变，两种凭证共用一套路由 | 头是隐式的，调试时容易忘；前端每个请求都要带 |
| C. 存在会话里 | 登录后选“当前组织”，写进会话 | 前端最省事 | 同一个浏览器开两个标签页操作两个组织时会互相覆盖（经典 bug） |

**权衡**：这里的关键是**对外 URL 是单向门**。按 ADR 0001，管理 API 有版本前缀，已经发出去的 `/api/v1/links` 不能随便改。

- A 是最“正确”的 REST 设计，但要么破坏现有调用方，要么上 `/api/v2`，为了一个内部需求付出版本迁移的代价。
- C 的状态放在了服务端会话里，而“当前组织”是**每个请求自己的属性**，放到会话这种跨请求的状态里，就会出现多标签页冲突。
- B 把“这个请求操作哪个组织”留在请求本身，又不改 URL。中间件验证“这个用户确实是这个组织的成员”，然后写进 context，handler 照旧。

**推荐 B。** 中间件对不是成员的组织返回 404，不返回 403，和链接的租户隔离一致：不暴露组织是否存在。

## 不需要选、按推荐直接做的部分

这些地方业界有明确的正确答案，列出来是为了知道为什么：

- **context 里的身份**：从 `tenant.Tenant` 扩展成一个 `Principal` 结构体，包括租户、执行者（用户或 API Key，带 ID）和权限集合。
  用结构体而不是接口：执行者只有两种，是封闭的集合，`switch` 比多态清楚。仓库约定“先用具体类型”（AGENTS.md）。
  Java 里会写一个 `Authentication` 接口加多个实现；Go 里接口由使用方定义，没有第二个使用方之前不抽。
- **CSRF**：会话放 Cookie 后，跨站请求会自动带上它。用标准库的 `http.CrossOriginProtection`（Go 1.25 起），
  它按 `Sec-Fetch-Site` 和 `Origin` 拒绝跨站的非安全方法请求。Cookie 同时设 `SameSite=Lax`。两层都要：后者是浏览器的行为，前者是服务端自己的检查。
  API Key 请求不带 Cookie，不受 CSRF 影响。
- **Cookie 属性**：`HttpOnly`（JS 读不到，挡住 XSS 偷会话）、`Secure`、`Path=/api/`、有过期时间。
  `SameSite` 用 `Lax` 不用 `Strict`：从身份提供方跳回回调地址是一次跨站的顶层 GET，`Strict` 下浏览器不带 Cookie，登录会失败。
- **路由**：`GET /api/v1/auth/login`（跳去身份提供方）、`GET /api/v1/auth/callback`、`POST /api/v1/auth/logout`、`GET /api/v1/me`。
  回调地址要登记在身份提供方那里，改它要同时改两边，按对外 URL 对待（ADR 0001）。nginx 已经把 `/api/` 转给 console，不用改。
- **授权码流程的三个随机值**，每次登录新生成，放在一个 10 分钟的 HttpOnly Cookie 里，回调时比对后立刻删除：
  - `state`：防 CSRF 登录，回调里的 state 必须和 Cookie 里的一致；
  - PKCE 的 `code_verifier`：授权码被截获也换不到令牌；
  - `nonce`：写进 ID Token，防止旧令牌被重放。
- **ID Token 校验**：签名（JWKS）、`iss`、`aud`、`exp`、`nonce` 都由 go-oidc 校验，handler 不手写 JWT 解析。
  ID Token 只在回调里用一次，用来建会话，之后不保存；会话仍然是决策点 3 的服务端会话。
- **会话 token**：和 API Key 一样，`crypto/rand` 生成，库里只存 SHA-256。每次登录都发新 token（防会话固定攻击）。
- **配置**：`OIDC_ISSUER`、`OIDC_CLIENT_ID`、`OIDC_CLIENT_SECRET`、`OIDC_REDIRECT_URL`。四个都为空时 console 不挂登录路由，只支持 API Key，现有部署不受影响；只配了一部分时启动失败。
- **引导**：见决策点 4，`console member invite` 预先登记邀请，首次登录时按已验证的邮箱兑现。

## 不做什么

- 不做密码登录：决策点 4 选了只用 OIDC，不存密码。
- 不做 GitHub 登录：它不是 OIDC，作为第二个提供方单独做（决策点 4b）。
- 不做按邮箱自动关联多个身份、SSO / SAML、MFA：MFA 由身份提供方负责。
- 不做邀请邮件：要先有阶段 13 的可靠后台任务。邀请先由运维命令和管理接口登记，人自己去登录。
- 不做自定义角色（决策点 5 的 B、C）。
- 不做页面：先只有 JSON API 和登录跳转，用浏览器走一次登录、用 curl 带 Cookie 验证。页面以后单独决定技术栈。
- 不改 `/r/{code}`：跳转仍然公开，redirector 不知道用户的存在。
- 不加数据库行级安全（RLS）：留到阶段 16，作为租户隔离的第二道防线。

## 怎么验证

- httptest 加假 OIDC 服务：登录跳转带上 state、PKCE challenge 和 nonce；回调在 state 不符、nonce 不符、签名错误、
  `aud` 不对、ID Token 过期时都不建会话；成功时建会话、删掉流程 Cookie。
- httptest：每个管理接口按角色和 scope 的放行和拒绝表；不是成员的 `X-Org-ID` 返回 404；
  带会话 Cookie 的跨站 POST 被 `CrossOriginProtection` 拒绝；API Key 请求带 `X-Org-ID` 时忽略这个头。
- 集成测试：登出、移出组织、改角色后，同一个会话的下一次请求立刻生效；邀请只在 `email_verified` 为 true 时兑现。
- `make smoke`：用 compose 里的 Dex 走一次真实登录，带 Cookie 和 `X-Org-ID` 创建链接，登出后 401；老 API Key 的全部冒烟步骤不变。

## 后果

- console 多了一类凭证和一个外部依赖（身份提供方）。身份提供方挂了只影响新登录，已有会话和 API Key 照常工作。
- 不存密码，也就没有找回密码；能不能登录取决于用户在身份提供方那里的账号。
- `tenant.Tenant` 在 context 里换成 `Principal`，鉴权、限流和全部管理 handler 要跟着改一次；之后加新的凭证类型不再动 handler。
- 存量 API Key 迁移成全部 scope，行为不变；`created_by` 为空表示是运维命令签发的。
- 修改 ADR 0009“以后的用户平台”第 1、3 条：平台在 console 里，不经过外部网关。
- 以后的练习：把 `Authorizer` 换成 Casbin 实现；加 GitHub 作为第二个提供方，对比 OAuth 2.0 和 OIDC。
